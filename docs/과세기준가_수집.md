## 금융투자협회 — 전 운용사·전 펀드 일별 과표기준가 (권장)

협회 전자공시의 **펀드공시 › 펀드기준가격 및 등락 › 펀드기준가격** 화면이 쓰는 서비스다.
ETF 를 포함한 모든 집합투자기구가 대상이고, 브라우저 없이 순수 HTTP 로 된다.

```
POST https://dis.kofia.or.kr/proframeWeb/XMLSERVICES/
Content-Type: application/xml
Referer: https://dis.kofia.or.kr/

<?xml version="1.0" encoding="utf-8"?>
<message>
  <proframeHeader>
    <pfmAppName>FS-DIS2</pfmAppName>
    <pfmSvcName>DISFundStdPriceSO</pfmSvcName>
    <pfmFnName>select</pfmFnName>
  </proframeHeader>
  <systemHeader></systemHeader>
  <DISCondFuncDTO>
    <tmpV30>20260901</tmpV30>   <!-- 기준일자 -->
    <tmpV11>A01048</tmpV11>     <!-- 운용사 코드. 비우면 전체 -->
    <tmpV3/><tmpV4/><tmpV5/><tmpV7/><tmpV12/><tmpV50/><tmpV51/>
  </DISCondFuncDTO>
</message>
```

### 응답 필드 (`<selectMeta>` 블록마다 1펀드)

```
tmpV1   운용사            미래에셋자산운용
tmpV2   펀드명            미래에셋TIGER LG그룹+증권상장지수투자신탁[주식]
tmpV3   펀드유형          주식형
tmpV4   설정일            20110309
tmpV5   설정원본(백만원)   46887
tmpV6   기준가격(원)       12902.58
tmpV7   ★ 과표기준가격(원)  7165.94
tmpV8   자산구성 주식      84546
tmpV9   자산구성 채권      0
tmpV10  자산구성 유동      614
tmpV12  표준코드(ISIN)     KR5225A04026
tmpV13  회사코드          A01048
tmpV14  기준일자          20260901
```

### 반드시 지킬 것

- 요청 파라미터와 응답 필드가 **둘 다 `tmpV{n}` 인데 의미가 완전히 다르다.**
  요청의 `tmpV3` 는 미사용, 응답의 `tmpV3` 는 펀드유형이다. 헷갈리면 엉뚱한 값을 읽는다.
- 응답 앞부분에 **레코드 수만큼 `<extlist>` 더미 블록**이 먼저 나온다(그리드 버튼 상태값).
  실제 데이터는 그 뒤 `<selectMeta>` 다. 앞 몇십 KB 만 읽고 판단하면 "데이터 없음" 으로 오판한다.
- 응답이 크다. 미래에셋 하루치가 **2,836건 / 약 3.9MB**. 운용사 전체면 훨씬 커진다.
  `r.read()` 를 청크로 끝까지 돌려야 하고, 한 번에 다 받지 말고 **운용사(`tmpV11`)별로 끊는다.**
- `tmpV51` 은 페이징이 아니라 필터처럼 동작한다(30 을 넣으니 총건수가 2 로 줄었다). 건드리지 말 것.

### 표준코드 주의

`tmpV12` 는 **펀드 설정 표준코드**(`KR5225A04026`)이고, 세이브로가 주는 **상장 ISIN**(`KR7133690008`)과 다르다.
ETF 6자리 단축코드로 바로 잇지 못하므로 **펀드명 매칭이 필요**하다.
(예: `미래에셋TIGER 미국나스닥100증권상장지수투자신탁` ↔ `TIGER 미국나스닥100`)

### ★ 과세표준액 역산은 실패했다 (2026-09-02 검증)

"과세표준액 = 과표기준가 낙차" 로 역산해 ETF CHECK 를 대체하려 했으나 **쓸 수 없다.**
TIGER 14종 28회차를 ETF CHECK 실측값과 대조한 결과:

| 방식 | 적중 |
|---|---|
| 배당락일 전 4영업일 중 최대 낙차 | 21/28 (75%) |
| 배당락일 직전 영업일(D-1) 낙차 | 18/28 (64%) |

낙차가 정확히 맞는 회차도 많다. TIGER 200커버드콜OTM 은 8/26 10,071.59 → 8/27 10,000.66
= **−70.93**, 실측 과표 **71원** 으로 딱 떨어졌다. 문제는 일관성이 없다는 것이다.

- **낙차 발생일이 종목·회차마다 다르다.** D-2 에 떨어지기도, 배당락일 당일에 떨어지기도 한다.
- **과표기준가는 분배 말고도 매일 움직인다.** 환헤지 손익·평가손익이 섞여 분배분만 못 가른다.
  TIGER 미국30년국채커버드콜액티브(H) 는 실측 과표 0 인데 낙차는 −5 였다.
- 전액과세(과표 = 분배금) 회차에서 오히려 낙차가 안 보이는 경우가 잦았다.
  TIGER 미국배당다우존스 7/30 분배 37 · 실측 37 인데 7/28→7/29 는 오히려 올랐다.

세금 계산에 쓰는 값이 4건 중 1건 틀리면 안 된다. **ETF CHECK 수집은 계속 필요하다.**

### 세이브로 결산과표기준가로도 안 된다 (식 전수 대입)

세이브로가 주는 `TAXSTD`(결산과표기준가) 연속값으로 과세표준액을 역산할 수 있는지
5종목 30회차에 식을 전부 대입했다. **아무것도 기준선을 못 넘었다.**

```
ΔP                          13/30 (43%)
-ΔP                          7/30 (23%)
ΔP + 분배금                  11/30 (37%)
ΔP + 직전과표 (재귀)          16/30 (53%)
ΔP + 직전과표 + 분배금        17/30 (57%)
전액과세 (분배금 그대로)      18/30 (60%)  ← 기준선
전부 0                        8/30 (27%)
```

이유는 분명하다. 국내상장 해외ETF 의 과표기준가에는 **평가손익이 섞여 있어**
회차 간 변동(±400원)이 과세표준액(0~133원)을 완전히 덮어버린다.
`483290` 은 시장이 올라 전액과세, `476850` 은 과표기준가가 거의 안 움직여 과표 ≪ 분배금,
`453850` 은 기준가가 내려 과표 0 — 방향은 맞지만 금액을 못 뽑는다.

### 결론

**분배금별 과세표준액은 ETF CHECK 가 여전히 유일한 경로다.**

| 후보 | 결과 |
|---|---|
| 세이브로 결산과표기준가 | ❌ 역산 불가 (위) |
| 금융투자협회 일별 과표기준가 | ❌ 낙차 역산 64~75% |
| 운용사 분배금 공시 | ❌ 게시가 늦고, 아예 안 올리는 운용사가 있다 |
| KRX 정보데이터시스템 | ❌ 없음 — 로그인 후 메뉴 전수 확인 (아래) |

## KRX 는 없다 (로그인 후 전수 확인, 2026-09-02)

### 먼저: KRX 는 전면 로그인제가 됐다

`data.krx.co.kr` 이 모든 통계에 로그인을 요구한다. 페이지 소스에 판정이 그대로 있다.

```js
if (!isLogin && menu_id.indexOf("MDC01") == -1) {
    alert('로그인 또는 회원가입이 필요합니다.');
}
```

`MDC01`(메인·쉽게보는통계)만 열려 있고 **`MDC02` = 기본통계 전체가 로그인 필요**다.
그동안 막혔던 게 전부 이것 하나였다 — `getJsonData.cmd` 400, pykrx 빈 응답,
`KRX 로그인 실패: KRX_ID 또는 KRX_PW 환경 변수` 경고, 브라우저 렌더 멈춤.

pykrx 최신판은 `login_krx(os.getenv("KRX_ID"), os.getenv("KRX_PW"))` 로 로그인을 지원한다.
**계정(무료 가입)만 있으면 자동화가 다시 열린다.**

### 로그인해서 확인한 결과

기본통계 메뉴 **317개 전수** 검색:

```
'분배'      0건
'과세'/'과표' 0건
'배당'      3건 — PER/PBR/배당수익률, 동(개별종목), 배당종목 현황 (전부 주식용)
```

증권상품 › ETF 하위 18개 메뉴도 전부 시세·등락률·거래실적·PDF·괴리율·추적오차·LP평가뿐이다.

```
전종목 시세 / 전종목 등락률 / 개별종목 시세 추이 / 전종목 기본정보 / 개별종목 종합정보
투자자별 거래실적(±개별종목) / PDF / ETF 상세검색 / 액티브ETF 실적 / 액티브ETF 편입자산현황
추적오차율 추이 / 괴리율 추이 / 장마감 괴리율 추이 / 합성ETF 거래상대방 위험
합성ETF 기초지수 및 담보 관리 / 분기별 LP평가
```

응답 필드도 직접 확인했다. `MDCSTAT04601`(ETF 전종목 기본정보, 1,167종)에
`TAX_TP_CD`(과세유형 **코드**)가 있지만 금액이 아니다.
`04301`(전종목시세)은 `NAV` 까지만이고 과표기준가도 없다.

**KRX 는 분배금도 과세표준액도 제공하지 않는다.** 분배는 거래소가 아니라
발행사(운용사)·예탁결제원 영역이라 그런 것으로 보인다.

## 증권사 경로 (2026-09-02 확인)

### ★ 증권사 HTS 에는 있다 — SK증권 주파주 [5135]

`ETF/ETN 종목별 과표기준가 조회`. 컬럼이 이렇다.

```
일자 | 종목명 | 과세유형 | 과표기준가 | 배당전과표기준가 | 주당배당액
```

**같은 날짜 한 줄에 배당 전/후 두 값이 다 있다.**

```
주당 과세표준액 = 배당전과표기준가 − 과표기준가   (상한: 주당배당액)
```

위에서 낙차 역산이 64~75% 에 그친 이유가 여기서 드러난다.
나는 **전일 종가 과표기준가 − 당일 과표기준가**를 뺐고, 그 하루치 평가손익·환헤지 손익이
과세표준액(0~133원)을 덮어버렸다. 증권사는 같은 날 배당 전/후 값을 받으므로 오차가 0 이다.
**방법론이 틀린 게 아니라 입력이 하나 모자랐다.**

조회 조건: 전체선택 · ETF · 과세유형 배당소득세 · 기간 지정. 그리드 → 엑셀 저장.
화면검색창에 "과표" 를 치면 다른 증권사에도 같은 화면이 있다(코스콤 공통 데이터).

#### ★ 검증 완료 (2026-09-02, 3종목)

2026-08-31 기준일 분배분을 세이브로 실측과 대조했다. **3/3 정확히 일치.**

| 종목 | 배당전과표기준가 | 과표기준가 | 차이 | 주당배당액 | 세이브로 분배금 | 과표율 |
|---|---|---|---|---|---|---|
| 453850 ACE 미국30년국채액티브(H) | 8,256.15 | 8,256.15 | **0** | 2,600.00 | 26원 | 0% |
| 459580 KODEX CD금리액티브(합성) | 1,075,780.01 | 1,073,022.01 | **2,758** | 275,800.00 | 2,758원 | 100% |
| 458730 TIGER 미국배당다우존스 | 15,387.98 | 15,357.98 | **30** | 3,000.00 | 30원 | 100% |

453850 의 과표 0 은 예전에 ETF CHECK 실측으로 확인한 값과도 같다.
**전액과세 종목과 과표 0 종목을 정확히 갈라낸다 — 공식이 진짜로 작동한다.**

```
과세표준액(원) = 배당전과표기준가 − 과표기준가
분배금(원)     = 주당배당액 ÷ 100        ← ★ 한 줄 안에서 단위가 다르다
```

`주당배당액` 만 100배로 표기된다(3,000→30 / 2,600→26 / 275,800→2,758, 3건 연속 확인).
과표기준가 두 칸은 원 단위 그대로다.

#### 날짜 매핑

**행은 배당락일에 나온다.** 세이브로 지급기준일의 직전 영업일이다.

```
세이브로 RGT_STD_DT 2026-08-31(월)  ↔  HTS 일자 2026-08-28(금)
```

배당 없는 날은 `배당전과표기준가`·`주당배당액` 이 0.00 이므로,
**`주당배당액 > 0` 인 행만 추리면 그게 곧 분배 회차 목록**이다.

#### 한계 — 대량 수집은 못 한다

- **페이징이 130행씩**이다. 전체 조회는 `종목 × 영업일` 이라 7일치만 잡아도 수십 페이지가 된다.
  엑셀 저장도 현재 로드분만 나온다.
- **신한 SOL HTS 에는 이 화면이 없다.** 확인된 건 SK증권뿐이다.
- 신한 SOL HTS 는 **화면 캡처가 차단**돼 있다(nProtect 계열). 창이 최상단인 건 확인되는데
  캡처하면 검은 화면만 나와서 computer-use 로 대신 조작할 수 없다.

그래서 **수집은 ETF CHECK, 검산은 SK증권 [5135]** 로 역할을 나눈다.

#### ★ ETF CHECK 는 약 300건에서 차단된다 (2026-09-02 실측)

`/mobile/etpitem/{code}/cash/hist` 를 Claude-in-Chrome 5탭으로 연속 조회했다.
로그인 불필요하고 **272종까지는 잘 받았다.** 그런데 약 300 요청 지점에서 막혔다.

**에러가 아니라 빈 결과로 돌아온다.** HTTP 200 에 표 구조도 그대로인데 본문만
`배당 내역이 없습니다` 로 바뀐다. 그래서 "이 종목은 원래 배당이 없나 보다" 로 오판하기 쉽다.

판별법 — **이미 성공했던 종목을 다시 조회해 본다.**
458730 은 38행을 받았는데 차단 후 같은 URL 이 0행 + `배당 내역이 없습니다` 를 돌려줬다.
종목 문제가 아니라 차단이라는 결정적 증거다.

차단 중에 빈값으로 읽힌 종목을 저장하면 과표가 0(비과세)으로 들어가 **세금을 과소 계산**한다.
저장 로직에서 빈 배열은 반드시 스킵할 것.

**운영 규칙**: 한 번에 250종 이하, 세션을 나눠서. 전 종목(977종)을 한 번에 긁으려 하지 말 것.

## ★ FunETF — 삼성 계열 과표 공개 API (2026-09-02 확보)

`funetf.co.kr` 이 **삼성자산운용 계열(KODEX·KoAct) 202종**의 과세표준액을 공개 API 로 준다.
로그인 없이 되고 차단도 없다. ETF CHECK 가 막혔을 때의 대체 경로다.

```
1) 전 종목 목록 + ISIN
   GET /api/public/product/etf/distributionCheck/list?...&size=2000
   → content[] 에 955종. sotCd(단축코드) → itemId(ISIN) 매핑을 여기서 만든다.

2) 종목별 분배 이력 (상장 이후 전체)
   GET /api/public/product/view/etfdividend?itemId={ISIN}
   → [{gijunYmd, divAmt, taxDividAmt, divRt, ...}]
```

- **`taxDividAmt` 가 주당 과세표준액**이다. `gijunYmd` 는 이름과 달리 **배당락일**이다(ETF CHECK 와 같은 날짜).
- **`itemId` 는 ISIN 이어야 한다.** `sotCd`(단축코드)로 넣으면 200 에 빈 배열이 온다. ISIN 은 반드시 1)에서 받아 쓸 것 — Luhn 으로 계산하면 틀린다.
- **삼성 계열만 값이 있다.** TIGER·ACE·RISE·PLUS·SOL·KIWOOM 은 필드는 있는데 전부 `null`.
- PC 웹 화면에서는 `주당 과세 표준액` 열이 `display:none` 이라 안 보인다. **API 에는 있다.**

### 교차검증 — 코스콤 vs 삼성운용

ETF CHECK(코스콤 경로)와 FunETF(삼성운용 경로)가 겹치는 86종 1,160행을 대조했다.

```
일치   1,157행 (99.7%)
불일치     3행 — 441640 과표 39 vs 38, 481050 분배금 2810 vs 2805 (반올림·표기 차이)
```

**경로가 다른 두 소스가 사실상 완전히 일치한다.** 지금까지 확보한 과표 데이터를 신뢰해도 된다는 첫 실증이다.

### 운용사 자체 API 는 기대하기 어렵다

**TIGER(213종) 확인 — 없다.** 자사 사이트가 쓰는 ajax 는 `profit`·`price`·`pdf` 셋뿐이고 분배 관련 엔드포인트가 아예 없다. `price.ajax` 가 주는 건 **일별 과세기준가**지 과세표준액이 아니다.

과표는 운용사가 산출해 예탁결제원→코스콤으로 넘기는 원천징수용 값이라, 운용사 홈페이지는 대개 분배금만 보여주고 과표는 **분배 공지 게시글**에만 적는다. 삼성이 데이터로 뿌리는 게 예외다.
→ 남은 경로는 `etf-distribution-checker` 가 이미 긁고 있는 **12개사 분배 공지 본문**이다(미확인).

#### 참고 — ETF CHECK 도 코스콤이다

etfcheck.co.kr 은 코스콤이 운영한다. 증권사 HTS 데이터도 코스콤에서 온다.
**같은 DB 를 두 창구로 보는 것**이라 값이 3/3 일치한 건 당연하다.
따라서 HTS 대조는 **독립 검증이 아니다** — 잡히는 건 내 수집·파싱 오류뿐이고,
코스콤 원본이 틀리면 둘 다 똑같이 틀린다.

진짜 독립 검증은 **실제 원천징수 결과**뿐이다.

```
과표 = (세전 배당금 − 실수령액) ÷ 0.154
```

증권사 앱 배당 내역에 세전·세후가 다 나온다. 계산 경로가 완전히 다르므로 이것만이 교차검증이 된다.

#### 이걸로 ETF CHECK 가 불필요해진다

차단 위험 0(본인 계좌 조회 화면), 커버리지 전 종목, 과거 이력까지 기간 지정으로 소급된다.

### 증권사 오픈 API 는 전부 없다

| 증권사 | 확인 방법 | 결과 |
|---|---|---|
| 한국투자 KIS Developers | `open-trading-api` 저장소 전체 grep | `과표`·`과세` **0건** |
| 키움 REST OpenAPI | 가이드 문서 grep | **0건** |
| 토스증권 Open API | `openapi.json` 33개 엔드포인트 전수 | **0건** |

토스는 `기준가` 가 7회 나오지만 전부 **등락률용 전일 기준가**, `tax` 13회는 전부 **거래세**다.
배당·분배 항목 자체가 없다. 시세·종목마스터·계좌·주문뿐이다.

**패턴이 일관된다 — 시세는 열고 과세 데이터는 안 연다.**
배당전과표기준가는 운용사 → 예탁결제원 → 코스콤 → 증권사 내부망으로만 흐른다.

### 참고: 내 계좌 원천세로 역산은 된다 (전 종목은 안 된다)

토스 웹앱 전용 API `dividends` 는 **내 계좌가 받은 배당의 세전·세후·원천세**를 준다.

```
과표 = (세전 − 세후) ÷ 0.154
```

이미 받은 회차·내가 보유한 종목만이라 데이터 소스로는 못 쓴다.
다만 **다른 경로로 얻은 과표를 검증하는 데는 쓸 수 있다.**

### 반드시 지킬 것

- **`Content-Type: application/xml`.** `application/x-www-form-urlencoded` 로 보내면

- **`START_PAGE` 는 페이지 번호가 아니라 행 오프셋**이다. 한 번에 30건 고정.
  1 → 31 → 61 … 로 올린다. `END_PAGE` 를 키워도 30건을 넘지 않는다.
- **필드명이 값과 어긋난다. 이름만 보고 매핑하면 틀린다.**

```

RGT_RSN_DTAIL_NM       배당구분 (이익분배 등)
```

## 과세표준액은 여전히 ETF CHECK 뿐

세이브로의 `TAXSTD` 는 **결산과표기준가(가격)** 이지 과세표준액(분배금 중 과세 대상)이 아니다.
회차 간 차이로 역산도 안 된다.

```
KoAct 배당성장액티브(476850) 2026/07 분배 290원 · ETF CHECK 과표 9원
  세이브로 결산과표기준가 9,822.03(6월) → 9,840.29(7월) = +18.26
  → 9원과 맞지 않는다. 일별 과표기준가가 없으면 발생액을 못 가른다.
```

과표가 분배금보다 크게 낮은 건 커버드콜·채권·금리형이고 그 유형은 트래커 189종에 이미 전수 들어 있다.
**모르는 종목은 `과표 = 분배금`(전액과세)으로 두면 세금을 크게 잡는 쪽이라 안전하다.**

# 일별 과세기준가 (TIGER 한정)

ETF 분배금의 과세표준액을 구하려면 **과세기준가(과표기준가격)** 일별 시계열이 필요하다.
그동안은 ETF CHECK를 브라우저로 돌아 분배 회차별 과표만 긁어 왔는데(`ttokjae-tax-base-updater`),
운용사 공시에서 일별 과세기준가를 직접 받는 경로를 찾았다.

## 왜 일별 과세기준가가 더 나은가

```
과표증분        = 기간말 과세기준가 − 기간초 과세기준가
분배금 과세표준액 = min(분배금, 해당 기간 과표증분)
```

회차별 과표를 받아오는 것보다 일반적이다. 아무 기간이나 잡아 계산할 수 있고,
매도 시 과세표준(국내상장 해외ETF 매매차익)도 같은 값으로 구한다.

## TIGER (미래에셋) — 확인 완료 2026-09-02

브라우저 없이 순수 HTTP로 된다. WAF·로그인·쿠키 전부 불필요.

```
POST https://investments.miraeasset.com/tigeretf/ko/product/search/detail/price.ajax
Content-Type: application/x-www-form-urlencoded; charset=UTF-8
X-Requested-With: XMLHttpRequest
Referer: https://investments.miraeasset.com/tigeretf/ko/product/search/detail/index.do

ksdFund={ISIN}&startDate=YYYYMMDD&endDate=YYYYMMDD
```

- **날짜는 하이픈 없이 `YYYYMMDD`.** `2026-08-01` 로 보내면 조용히
  "검색 결과가 없습니다" 를 돌려준다. 에러가 아니라 빈 결과라 놓치기 쉽다.
- 응답은 JSON 이 아니라 **HTML 조각**이다. `<tr>` 안의 `<td>` 를 순서로 읽는다.

```
td[0] 날짜(2026.09.01)  td[1] 시장가격 종가  td[2] 전일대비
td[3] 기준가격(NAV)     td[4] 전일대비       td[5] 과세기준가(원)
td[6] 기초지수 종가     td[7] 전일대비
```

실제 응답 예 (133690 TIGER 미국나스닥100):

```
2026.09.01  시장가 178,785  NAV 178,699.71  과세기준가 178,700.50
2026.08.31  시장가 178,540  NAV 178,321.64  과세기준가 178,334.46
```

### 찾은 방법

페이지 HTML(`urllib` 로 받은 162KB)에는 과세기준가가 없다. JS 가 나중에 채운다.
Chrome 에서 `XMLHttpRequest.prototype.open/send` 를 후킹한 뒤 `#section4` 의 **조회** 버튼을
누르니 위 요청이 잡혔다. 네트워크 탭만 봐서는 정적 자원에 묻혀 안 보였다.

### ISIN 주의

`ksdFund` 는 종목코드가 아니라 ISIN 이다. `KR7` + 6자리코드 + `00` + 체크디짓 형태인데
**Luhn 으로 계산한 체크디짓이 실물과 다른 경우가 있다.**

```
133690 → 계산 KR7133690008 = 실물 KR7133690008  ✅
458730 → 계산 KR7458730009 ≠ 실물 KR7458730005  ❌
```

그런데 **틀린 체크디짓으로도 응답은 정상으로 왔다.** 서버가 앞 11자리만 보는 듯하다.
운에 기대는 것이라, 실제로 쓸 때는 ISIN 을 별도로 확보하는 편이 안전하다.
(pykrx `get_etf_isin`, 또는 etf-selector 마스터에 ISIN 열 추가)

## 남은 숙제

- **TIGER 외 운용사.** KODEX(삼성)·ACE(한투)·RISE·PLUS·SOL·KIWOOM 등은 각자 다른 사이트다.
  KODEX 는 `/etf/product/distribution.do` 엔드포인트를 발견했으나 과세 문구는 못 찾았다.
  `etf-distribution-checker` 스킬이 이미 12개 운용사를 돌고 있으니 거기 붙이는 게 빠를 수 있다.
- **금융투자협회** `https://dis.kofia.or.kr/proframeWeb/XMLSERVICES/` 는 게이트웨이가 살아 있고,
  `pfmAppName`/`pfmSvcName` 이 틀리면 `proframe application name [X] [Y] is not found` 를
  친절히 돌려준다. 올바른 서비스명만 알면 전 운용사를 한 곳에서 받을 수 있다.
  화면 XML(`/wq/fundann/*.xml`) 직접 접근은 막혀 있어 서비스명을 못 캤다.
- **KRX 정보데이터시스템**은 이 작업 환경(리눅스 샌드박스)에서 빈 응답만 온다.
  pykrx 도 같은 증상. 사용자 PC 나 GitHub Actions 러너에서는 될 수 있다.
